2. Estrutura de pastas

Separei configuração (config/) de aplicação (portfolio/). É o padrão que o próprio Django recomenda e facilita muito plugar um segundo app depois (um blog, por exemplo). 

portfolio-django/
├── config/                 # configuração do projeto
│   ├── settings.py         # tudo por variável de ambiente
│   ├── urls.py             # rotas raiz + health check
│   ├── wsgi.py             # entrada usada por Gunicorn e Vercel
│   └── asgi.py
├── portfolio/              # meu app
│   ├── models.py           # Perfil, Habilidade, Projeto, Mensagem
│   ├── views.py            # Class-Based Views
│   ├── forms.py            # formulário de contato + honeypot
│   ├── urls.py             # rotas do app (namespace "portfolio")
│   ├── admin.py            # painel de conteúdo
│   ├── context_processors.py
│   ├── tests.py            # testes automatizados
│   └── management/commands/carregar_dados.py
├── templates/              # HTML (base + páginas + partials)
├── static/                 # CSS, JS, imagens
├── docs/                   # README, ARQUITETURA, DEPLOY

3. Modelos de dados

Quatro modelos, cada um espelhando uma parte visível do site:

  • Perfil — meus dados (hero, sobre, links). Tabela de uma linha só; o admin bloqueia a criação de um segundo perfil.
  • Habilidade — tecnologia com categoria, nível (0–100) e ordem de exibição.
  • Projeto — título, slug único, resumo, descrição, linguagem, tecnologias, links e as flags publicado e destaque.
  • Mensagem — o que chega pelo formulário de contato, somente leitura no admin.

Criei um QuerySet próprio com publicados() e destaques() para não repetir o mesmo filtro em cada view: 

class Publicado(models.QuerySet):
    def publicados(self):
        return self.filter(publicado=True)

    def destaques(self):
        return self.publicados().filter(destaque=True)


class Projeto(models.Model):
    # ...
    objects = Publicado.as_manager()   # Projeto.objects.destaques()

5. Rodando localmente

# 1. clonar e entrar na pasta
git clone https://github.com/JuniorSilva88/portfolio-django.git
cd portfolio-django

# 2. ambiente virtual
python -m venv .venv
source .venv/bin/activate        # no Windows: .venv\Scripts\activate

# 3. dependências
pip install -r requirements.txt

# 4. banco e conteúdo
python manage.py migrate
python manage.py carregar_dados          # popula perfil, stack e projetos
python manage.py createsuperuser         # acesso ao /admin

# 5. subir
python manage.py runserver
# http://127.0.0.1:8000

O comando carregar_dados aceita --github para importar meus repositórios ao vivo da API pública do GitHub, e --limpar para recriar o conteúdo do zero. Ele é idempotente (usa update_or_create), então rodar duas vezes não duplica nada.

7. Deploy no Render

No Render eu rodo a aplicação inteira (com banco Postgres e admin funcionando). O arquivo render.yaml já descreve o serviço, então dá para usar o modo Blueprint e não configurar nada na mão. 

# Build Command
pip install -r requirements.txt && python manage.py collectstatic --noinput && python manage.py migrate

# Start Command
gunicorn config.wsgi:application --bind 0.0.0.0:$PORT

# Health Check Path
/healthz
  • Crio um Postgres no Render e ligo a DATABASE_URL no serviço web.
  • Defino SECRET_KEY, DEBUG=False e ALLOWED_HOSTS.
  • Depois do primeiro deploy, rodo python manage.py carregar_dados no Shell do Render para popular o conteúdo.

8. Deploy na Vercel

Na Vercel o Django roda como função serverless Python: o vercel.json manda todo o tráfego para api/index.py, que apenas expõe o WSGI do projeto. 

# api/index.py
from config.wsgi import application
app = application          # a Vercel procura por "app"

Dois pontos que eu documento porque já me pegaram:

  • O sistema de arquivos é somente leitura — SQLite não funciona. Na Vercel eu aponto DATABASE_URL para um Postgres gerenciado (Neon, Supabase ou o próprio Render).
  • Sem banco de escrita, o formulário de contato e o admin não gravam. Por isso trato a Vercel como vitrine e o Render como ambiente completo.

9. Boas práticas aplicadas

  • Configuração por ambiente: o mesmo código roda local, no Render e na Vercel só trocando variáveis.
  • Segurança: com DEBUG=False eu ligo HSTS, cookies seguros, redirect para HTTPS, nosniff e proteção de clickjacking. CSRF em todo formulário.
  • Templates sem repetição: um base.html, partials para header/footer/card.
  • Sem consulta duplicada: filtros ficam no QuerySet do modelo e dados globais no context processor.
  • Acessibilidade: HTML semântico, aria-label nos botões de ícone, foco visível, link "pular para o conteúdo", contraste conferido e respeito a prefers-reduced-motion.
  • Responsividade: clamp() na tipografia e no espaçamento, grade automática com auto-fill e apenas dois breakpoints.
  • Performance: CSS e JS comprimidos com hash no nome, JS com defer, animação por IntersectionObserver em vez de evento de scroll.
  • Conteúdo editável: tudo pelo admin, sem novo deploy para trocar um texto.
  • Código comentado: cada arquivo explica a decisão, não só o que a linha faz.

10. Testes

Cobri o essencial: modelos, views, filtros e o formulário de contato.

python manage.py test          # roda toda a suíte
python manage.py check --deploy  # checklist de segurança para produção

O check --deploy é o meu último passo antes de publicar: ele avisa se ficou alguma configuração insegura para produção.
